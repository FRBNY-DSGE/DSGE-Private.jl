# Chain safety (scripts/run.sh, tested on this site by tests/test_exitcodes.txt, jobs 343093-343096):
#   - julia runs under `timeout WALL`; on the wall limit run.sh exits 99 -> SGE requeues the SAME job, which resumes from
#     its newest loadable stage file (INCREMENT = 1). Jobs held on it keep waiting.
#   - any failure (error, HEALTH_FAIL = exit 2) -> run.sh exits 100 -> the job goes to error state (Eqw) and every later
#     job, held with -hold_jid on it, STAYS held. A plain non-zero exit would have released the next step (review §6 a).
#     Inspect the log, then (RTWALK104-FIXVERIFY N1; tested on this site, RTWALK104-N123):
#       * after an ERROR exit (no HEALTH_* marker in the step dir): fix the cause, then `qmod -cj <jobid>`; the step
#         resumes from its newest loadable stage file.
#       * after a HEALTH_FAIL (marker steps/<t>_to_<t+1>/HEALTH_FAIL): `qmod -cj` ALONE IS NOT ENOUGH (step.jl finds the
#         marker, exits 2, back to Eqw). Add the redo variables, then clear:
#           qalter -adds v HEALTH_REDO 1 -adds v H_POLISH <k> <jobid>
#           qmod -cj <jobid>
#         Use `-adds v KEY VALUE` (adds, or overwrites an existing KEY; `-mods v KEY VALUE` also overwrites), not
#         `qalter -v ...`: per `man qsub`, -v "defines or redefines" the variable list, so it may drop NW, WALL, ORIGIN,
#         SEED_CLOUD, FRBNY_NW. (In the N123 test, job 343118, `qalter -v C=3` happened to keep A and B, but -adds is the
#         documented additive form.) The bridge file is complete, so only the health check reruns.
#       * or `qdel` the job together with its dependants.
#   - steps 4-25 (FRBNY_NW=96), after any requeue (exit 99) or Eqw (RTWALK104-FIXVERIFY N4): if the master was killed
#     while its FRBNY worker job was still PENDING, that worker job (name julia-<pid>, cwd $R/workers) stays queued and
#     would later start, hold 96 slots until its workers give up on the dead master (JULIA_WORKER_TIMEOUT = 300 s in
#     the job env here: about 8 slot-h and a few minutes of queue delay per orphan), then exit. run.sh lists such jobs in the step log ("N4 WARNING"); it never
#     deletes them. Check `qstat -u $USER | grep julia-` and `qdel` a stray one by hand (only a pending julia-* job whose
#     `qstat -j <id> | grep ^cwd` is $R/workers and that the current master did not submit: compare with the
#     "worker job" id in the current step log / the newest julia-<pid>).
#   - -r y: requeued after a node failure. WALL < h_rt < the FRBNY worker cap (38.27 h); the worker job gets
#     h_rt = 38:00:00 (step.jl, frbnyjuliamemory = "8G,h_rt=38:00:00").
#   - second line of defence: step.jl refuses a walk seed whose step directory has no HEALTH_PASS.
